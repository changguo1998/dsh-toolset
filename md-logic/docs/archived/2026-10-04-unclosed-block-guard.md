## 调研（已核）

- 现象：`content` 里写未闭合的代码围栏或 `<!--`，CommonMark 会把它之后的所有行并进该块——**写入后其后节从节树消失**，而既有守卫（① 标题行 / ①.5 层级）都不拦：吞并发生在 parser 内部，解析结果只是「少了几节」，不报错。
- 为什么必须拦：这是**静默结构破坏**（用户看不到错误，节却没了）；与 ①.5 层级守卫同族（都是「content 写法会改变其后节的归属」）。
- 配对语义（CommonMark 够用子集）：围栏 `^ {0,3}(` + 三连反引号/波浪号 + `)` 开，闭行须**同字符**、长度 ≥ 开栏且不带 info 串；`<!--` 需 `-->` 配对（可跨行）。行内代码里的 `` `<!--` `` 不是注释（CommonMark 先解析 code span）。

## 决策

1. **在 ①.5 守卫里加「内容级配对检查」**（放在层级 / stray 检查**之后**：那两条更贴目标节，错误优先级保持不变），失败码复用 `content_invalid`，错误文案给出**行号 + 成因 + 替代路径**（`hash_edit` / 官方 `edit`）。
1. **扫描口径刻意保守**（宁可少报也不误伤）：围栏内不扫注释；行内代码先剥离再找 `<!--`；闭行要求同字符 + 长度 ≥ 开栏 + 无 info。放行面写进 README，便于用户判断「为什么这次没拦」。
1. **不校验其它 Markdown 语法**（本工具口径是「结构漂移安全」而非语法校验）：只拦「会吞掉其后节」的两种形态——这是导致节树静默变化的成因，其余语法问题各有其显式错误或无害。

### 审阅（第一轮，2026-10-04）

只读审阅（真实 parser 复现）结论「需修」：

1. **[重要] 漏拦：反引号围栏的 info 串含反引号**——CommonMark 规定反引号围栏的 info 不得含反引号，故 ```` ```a`b ```` 只是**普通文本行**；原实现把它当开栏 → 把**后面真正的开栏** ```` ``` ```` 误当闭行 → content 里其后节真被吞掉却**放行**（审阅用真实 parser 复现）。→ 新增 `fenceOpener()`：反引号围栏 info 含反引号时不算开栏（波浪号围栏无此限制）；补「漏拦面」用例（该形态现在被拒）。
1. **[次要] 误拒：注释判定过严**——原实现对**任意位置**的 `<!--` 都要求配对，且注释打开后仍认围栏；实测「正文中间的 `<!-- 没关`」「列表 / 引用行内」「4 空格缩进（代码块）」「```` <!-- 起 … ``` … --> ````」都不吞块却被拒（与「宁可少报也不误伤」的口径相反）。→ 注释开栏收紧为**行首（≤3 空格）**且同行无 `-->`；注释开栏期内**不认围栏**；三种误拒形态补进放行面用例。
1. **[提示]** 错误文案的行号改为「content **内**第 N 行」（原文案易读成文件行号）；`README.md` 多余空格与「宁可少报」措辞一并修订。已核无问题：CRLF、4 空格缩进围栏、波浪号围栏、四面套三面、围栏内 `<!--`、同行配对判定均正确；反向验证与越界情况正常。
