# 服务面包规划(新代)

## 目的

本文档梳理服务面的包结构与分层(最底层能力与基础能力), 及各服务面的职责与边界; 各服务面的接口工具清单见 SERVICES.md。

## agent 的最底层能力

| 能力     | 包名&服务名 |
| -------- | ----------- |
| 同步     | cSync       |
| 多级记忆 | cMemory     |
| 边界     | cBoundary   |
| 工具注册 | cTool       |
| 事件订阅 | cCascade    |
| 命令注册 | cCommand    |
| 增员     | cSpawn      |
| 会话目录 | cPath       |
| 解析     | cParse      |

### 什么是

agent 的最底层能力(够基础够底层, 封装宿主能力的也算)。每个能力对应一个新包(`包名 = 服务名`, 一包一服务): 单个抽象名词, 统一以 `c` 开头, 与宿主服务名及其它插件错开(`tool` / `command` 用单数避开宿主 `tools` / `commands`)。多数包以服务面挂载(`ctx.cXxx`); 少数只提供库面(cTool / cCommand: 经库导出 import 调用, 不挂 ctx 服务)。

### 什么不是

- 共享: 建在「同步」之上(跨会话的 KV / 消息传递依赖时间与顺序), 不是最底层能力。
- 任务执行 / 编排: 是「多级记忆 + 约束 / 边界」的组合派生, 不是原子能力。

### 同步(cSync)

- 要做什么: 共享资源的统一管理, 使多个 agent 观察到同一份状态: 登记共享资源(会话状态、队列、锁、时间、别名)的持有者与等待次序, 按时间与顺序发号取号(内含等待, 可带截止时间), 提供唤醒与串行化。别名(alias → sessionId, 无 TTL、用户意图)作为基础共享信息也归本层登记(aliasSet / aliasList / aliasClear); 会话启动后由会话自身经本层上报别名 / id(report), 供寻址与在线判定, 退出时撤销。上层不自行抢占资源, 一律经本层; 资源内容由上层定义; 唤醒源不限 agent。
- 后端: 跨进程用专用 Redis, 进程内串行用内存锁(promise 链), 本地排期与读钟(`now` / `schedule` / `interval`)是进程内底座、不依赖 Redis。
- 存续: 不落盘、不落文件, 只在 Redis 内存态; 需要存续的内容归 cMemory(写 G / P / S 持久层)。文件不归本层(留给 c-file / 宿主 fs 围栏)。
- 定时: 时间也是共享资源 —— 跨进程到点信号经本层 Redis 时间资源; 本地节律走进程内底座; 业务定时由 cPush.schedule / c-flow 消费。
- 和宿主的关系: 宿主会话各自独立, 跨会话共享资源既无登记处也无等待原语, 各插件只能自己搭一套。
- 不做什么: 不管资源里的内容(消息、KV 由上层定义), 也不替代宿主的会话持久化。

### 多级记忆(cMemory)

- 要做什么: 提供 全局(G)、项目(P)、会话(S)、上下文(C) 四级记忆存取, 并能注入当前上下文。一是按等级控制查询范围(全局 > 项目 > 会话 > 上下文, 上层按需查询); 二是集中维护记忆状态(G / P / S 三级落盘, 重启不丢失; C 级进程内保持, 跨压缩跨轮但重启丢失, 就是模型直接看到的上下文)。多 agent 一致视图不属本层, 归 cSync。
- 后端: 沿用 SQLite 三层库(全局 / 项目 / 会话, 惰性打开、可检索), C 级不落盘; 库路径定位与建目录经 cPath。
- 接口: `read`(G / P / S 读取)、`snapshot`(C 级保持项快照, 供展示层如 TUI 显示)、`write`(统一 `write(等级, 分类, ...)` 写 G / P / S 持久层)、`retain`(写 C 级内容, 动态保持注入, 写空字符串 = 撤销; 需长期固化直接写 S 级)。本层不提供注入工具(把内容投递到上下文归 cGuide / 上层消费方)。
- 和宿主的关系: 宿主只有单会话的事件日志与投影缓存, 没有跨会话跨项目的层级, 也没有压缩后仍能召回的那一层。
- 不做什么: 不改写会话日志, 不决定内容该存哪一级(由上层声明), 不提供多 agent 的一致视图。

### 边界(cBoundary)

- 要做什么: 汇聚宿主各步骤信息并统一唤醒, 供上层包做判别。
  - 汇聚: 订阅宿主工具执行链的各步骤(工具执行前 / 审批时 / 工具执行后), 按 callId / agent 关联成一份判别上下文。
  - 唤醒: 到判别时机把整份上下文喂给注册者, 注册者返回的判定(放 / 拦 / 送审)由本层转交宿主相应通道。
  - 次序: 同一时机多注册者按注册顺序串行 — 「拦 / 送审」短路, 「放」不否决, 全部「放」才放, 原因取先注册者。
- 和宿主的关系: 宿主把工具参数、审批请求、执行结果散在各钩子且互不关联, 本层统一订阅与关联, 消除手动接线。判别时机 / 顺序 / 口径由上层借这些时机实现。
- 不做什么: 不定义规则(规则本体与判定逻辑由注册方 / 具体规则插件声明, 有具体规则时新建规则包), 不改变宿主执行管道与沙箱, 不代理审批语义。

### 工具注册(cTool)

- 要做什么: 统一工具登记入口, 覆盖宿主的工具上下文管理策略。
  - 统一登记: 各工具包经 `cTool.register`(库面函数)登记, 内部完成判面可注册、套精简呈现(短说明 + 宽松占位)、全文与完整参数 schema 收进 catalog、注册进宿主; 缺面时告警降级, 各包不再手写判面与包装。
  - 精简呈现(minify 并入登记): 模型面只见短说明与宽松占位, 全文按需由消费方经 catalog 投递; 增删工具不扰动模型面的前缀与缓存。
  - 会话冻结: 工具列表在首条消息发出前定死, 会话期间不允许增删(运行期变化破坏缓存命中); 首条后的注册被拒绝或忽略。
- 和宿主的关系: 登记只包一层宿主 `ctx.tools` 接口, 无大改动; 宿主把完整工具定义静态写进上下文, 增删工具就改动前幂、缓存失效。
- 纯服务面: 本层无模型面工具; catalog 为包级, 模型面查询端(工具咨询包)import 库导出读取。
- 不做什么: 不改宿主执行管道, 不接管权限与审批; 不决定工具对哪些会话可见(可见性管理归工具咨询包, 经 cBoundary 注册判别拦截未揭示调用)。

### 事件订阅(cCascade)

- 要做什么: 统一订阅会话、回合、步骤、压缩等生命周期节点, 统一走一个订阅面; 频率控制是注册时的选项, 不单独提供服务面。
- 和宿主的关系: 宿主缺插件之间的订阅顺序契约。
- 不做什么: 不定义具体动作(由上层决定), 不做定时调度(定时唤醒归自主推进, 事件只是唤醒来源之一)。

### 命令注册(cCommand)

- 要做什么: 把命令的「结构声明 → 解析 → 路由」收成统一机制, 不再各插件手写 dispatch。
  - 登记(库面函数 register): 插件声明命令结构(命令名 + 多级子命令 + 参数 schema + 校验规则)与回调列表(每个子命令一个回调); 本层注册进宿主 `ctx.commands`, 结构收进包级目录。
  - 解析与路由(register 内部): 命令输入(宿主剥掉命令名后的整段原文)按结构拆出子命令与参数, 校验后路由到对应回调; 回调收到已校验参数, 不再见原始字符串。底层词法切段(引号 / 转义)经 cParse。
  - 补全支撑(库导出 completions): 把命令结构投影为结构化子命令表(含参数提示), 供 TUI 补全到子命令一级; 也是查结构的读口。
- 执行: 借宿主 `ctx.commands.execute`(进程内执行已注册命令、不发模型), 路由已注册在宿主里, 不另开执行接口; 本层不 provide 服务面(库面形态)。
- 和宿主的关系: 宿主 `ctx.commands` 只提供 register / list / find / execute, 列表只含 name 与 description, 子命令散在 `input.hint` 自由文本, 宿主只按命令名分发、不解析参数。
- 不做什么: 不做模型侧工具注册, 不实现命令内容与结果渲染(回调业务留插件), 不改动宿主命令服务本身。

### 增员(cSpawn)

- 要做什么: 提供独立进程会话的创建与退出(常驻形态, 宿主没有的能力)。
  - `create` 创建: 拉起独立进程会话并启动; 会话启动后经 cSync 上报自身别名 / id(身份登记), 可指定使用的模型、权限、cwd 等选项。
  - `exit` 退出: 停止进程并清理生命周期登记。
  - 进程内委派(一次性 / 可续)直接用宿主 `ctx.subagents`(subagent / subagent_fork), 本层不重复提供。
- 底座: 基底包含 `herdr-use` 的终端执行面(`herdrUse`), 但不提供模型侧工具(终端执行可绕过命令审查, 不能直接开放给模型)。
- 和宿主的关系: 宿主 `ctx.subagents` 只有进程内、由父会话管理的委派, 没有常驻成员与独立进程形态; 常驻会话的创建、身份认领与退出要自建。
- 不做什么: 不做任务分派与协作编排(不在本等级), 也不管成员之间怎么通信。

### 会话目录(cPath)

- 要做什么: 提供会话目录的解析与创建, 收敛各消费方的路径推导: 复刻宿主目录编码(`encodeSegment` / `projectKey` / `projectDir` / `sessionDir`), 按会话 id 取 `header.cwd` 推导目录; 带 ensure 选项时建目录(0700、幂等, 唯一写盘入口), 缺省只算不建。
- 和宿主的关系: 宿主把目录编码藏在 `session-persistence-jsonl` 内部不导出, `sessions` 只给会话仓库与 `header.cwd`; 新增的 `workingDirectory`(0.2.1)管工作目录变更, 不管 sessions 根路径, 均不替代本层。
- 不做什么: 不落盘会话内容, 不校验目录可写性, 不替代宿主会话持久化。

### 解析(cParse)

- 要做什么: 多语言语法理解底座, 自定服务接口, 后端用 tree-sitter: 语言识别、结构访问、命令目标 / 调用点提取。只做解析, 不做判定与改写。
- 失败语义: 解析器处理不了的内容不直接调模型 — 回执里带明确信号(语言 unknown / 空结构 / 空目标)并提示「可用模型解析」, 由上层消费方决定是否请模型兜底。
- 和宿主的关系: 宿主无多语言语法解析接口, 各插件只能各抄一份解析。
- 不做什么: 不管危不危险(判定由上层), 不改写代码(归 ast-tools), 不自行调用模型(兜底决定权在上层)。

## 基础能力(组合)

| 基础能力    | 包名&服务名 |
| ----------- | ----------- |
| 共享 / 通信 | cChannel    |
| 自主推进    | cPush       |
| 注入引导    | cGuide      |
| 约束        | cConstrain  |

在底层能力基础上组合出基础能力, 组合可以嵌套(已组合出的能力可再被更高层组合引用)。

### 共享 / 通信(cChannel)

组合: `cSync + cMemory`。

- 要做什么: 基于同步与记忆提供消息通信。
  - 消息传递(send): 一个会话向另一个会话发送消息, 作为同步共享状态经 cSync 送达、等待与唤醒; 需要跨进程存续时经 cMemory 落盘。
  - 消息接收(receive): 读目标会话的收件箱(经 cSync 的队列资源承载), 与 send 成对(推 / 拉)。
  - 寻址(lookup): 把稳定目标标识(会话 id / 别名)解析为在线目标会话; 别名(alias → sessionId)由 cSync 登记, 本层消费。
  - 共享内容: 不再单独提供 KV 方法 — 多会话共享内容直接经 cMemory(持久)+ cSync(一致性), 本层只做消息。
- 和宿主的关系: 宿主没有跨会话通道(只有只读的 `sessionQuery` / `sessionReference`), 同会话内的 peer mailbox 又出不了进程。
- 不做什么: 不做成员与归属管理(谁在组里、谁认领了什么), 那属于更高等级。

### 自主推进(cPush)

组合: `cSync + cMemory + cCascade`。

- 要做什么: 按阶段自行推进, 不依赖用户输入: `advance` 把推进切到「自动」状态并持续进行(经 cCascade 订阅的生命周期事件驱动, 持续注入提醒 — 固定提醒「查询并完成正在进行的任务」, 或取 c-flow 的 stage 目标描述反复提醒), 直到 c-flow 通过完工审查后调 `pause` 才停止; 经 cMemory 记住当前进度, 经 cSync 取得定时, 在需要时唤醒自己或继续循环。发起下一回合的一次性注入直接用宿主 `agents.followup`, 不依赖 cGuide(注入引导是上层组合服务, 不作本层底层)。
- 和宿主的关系: 宿主只有零散的单点能力(目标、计划状态、会话级提醒、后台作业), 没有「任务树 + 阶段顺序强制 + 验收」的推进模型, 唤醒也只回到原会话。
- 不做什么: 不判断活干得对不对(验收标准由上层给), 不自行收敛(推进开了就一直跑, 直到上层调 pause 关掉), 不做多 agent 的分派。

### 注入引导(cGuide)

组合: `cCascade`。

- 要做什么: 一类「字符串匹配 → 注入」规则的统一注册面 — 存在这类规则时不必为每个条件单独写一个包, 统一经 `cGuide.register` 注册(条件与注入内容都在配置里声明, 命中时投递该段配置内容)。匹配对象为会话节点的文本载荷(文本类节点 user-message / assistant-text / tool-call / tool-result, 规则可挂多个节点; 边界节点无条件命中)。投递经宿主 `agents.followup` 代替用户发一条消息引导行为; 判定时机与节流 / 去重经 cCascade。
- 和宿主的关系: 宿主的系统提示贡献面在装配期固定, 会话事件要自己订阅再写, 也没有命中条件、节流与去重。
- 不做什么: 不做硬拦截(拦是边界层面的事), 不提供命令。

### 约束(cConstrain)

组合: `cBoundary`(取其中的约束面)。

- 要做什么: 给控制流提供的拦截服务 — 控制流按阶段临时禁止某些工具(即使该工具已被揭示), 例如 plan 模式的只读阶段临时禁止写类工具; 这类拦截经 cBoundary 注册「工具执行前」判别, 命中即拦, 拦截的回执内容随之变化(说明阶段原因, 如「当前阶段只读」, 不是「工具不存在」)。
- 和宿主的关系: 宿主的计划模式只给只读段, 审批只管工具调用, 都不管计划范围与验收口径。
- 不做什么: 不做全局 / 策略性的工具准入(那由具体规则插件定义), 只做控制流阶段性的临时禁止; 不改系统提示。
