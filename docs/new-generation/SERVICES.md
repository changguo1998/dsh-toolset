# 架构梳理

## 目的

本文档用于梳理现在的项目结构, 并规划新的结构。

## agent 的最底层能力

| 能力 | 包名&服务名 |
|---|---|
| [同步](#同步csync) | csync |
| [多级记忆](#多级记忆cmemory) | cmemory |
| [边界](#边界cboundary) | cboundary |
| [工具注册](#工具注册ctool) | ctool |
| [事件订阅](#事件订阅ccascade) | ccascade |
| [命令注册](#命令注册ccommand) | ccommand |
| [增员](#增员cspawn) | cspawn |

### 什么是

agent 的最底层能力(够基础够底层, 封装宿主能力的也算)。每个能力对应一个新包(`包名 = 服务名`, 一包一服务): 单个抽象名词, 统一以 `c` 开头, 与宿主服务名及其它插件错开(`tool` / `command` 用单数避开宿主 `tools` / `commands`)。

#### 同步(csync)

- 要做什么: 共享资源的统一管理, 重点在于使多个 agent 观察到同一份状态: 登记共享资源(会话状态、队列、锁、文件)的持有者与等待次序, 按时间与顺序执行分配, 提供等待、唤醒与串行化。上层不自行抢占资源, 一律经本层; 资源内容由上层定义, 本层不处理。
- 和宿主的关系: 宿主的会话各自独立, 只有会话内事件与定时器; 跨会话的共享资源既没有登记处, 也没有等待原语, 各插件只能自己搭一套。
- 不做什么: 不管资源里的内容(消息、KV 由上层定义), 也不替代宿主的会话持久化。

#### 多级记忆(cmemory)

- 要做什么: 提供 全局、项目、会话、活跃 四个等级的记忆存取接口, 并能将内容注入当前上下文。侧重点在于内容的持久化与存取; 具备跨会话能力, 但多 agent 的一致视图不属于本层职责, 交由 csync 承担。
  - 一是通过不同等级的记忆, 实现记忆查询范围的控制: 四级为 全局 > 项目 > 会话 > 活跃, 上层按需要的范围查询, 不必自己拼装来源。
  - 二是集中维护记忆状态, 提供统一服务: 全局、项目、会话三级记录到文件, 进程重启也不丢失; 活跃级属于进程内记忆, 可以跨压缩、跨轮, 进程重启会丢失, 就是模型直接看到的上下文。
- 和宿主的关系: 宿主只有单会话的事件日志与投影缓存, 没有跨会话、跨项目的层级, 也没有压缩后仍能召回的那一层。
- 不做什么: 不改写会话日志, 不决定内容该存哪一级(由上层声明), 不提供多 agent 的一致视图(归 csync)。

#### 边界(cboundary)

- 要做什么: 提供约束与守卫接口, 供各上层包声明规则并挂载门禁。
  - 统一: 各包共用同一套接口, 不必各自造一套; 已声明的规则可被复用。
  - 复杂: 可以定义更复杂的控制规则, 覆盖顺序、范围、口径这类层面。
- 和宿主的关系: 宿主的守卫只落在工具调用这一个点(审批、沙箱、权限预设、读后改前), 管不到流程顺序、计划范围、输出规范这些层面。
- 不做什么: 不做具体的规则判定(规则内容由上层包声明), 也不代替审批应答。

#### 工具注册(ctool)

- 要做什么: 覆盖宿主的工具上下文管理策略, 实现两个目的。
  - 提高缓存命中率: 减少增删工具对前缀与缓存的扰动。
  - 压缩上下文长度: 精简工具定义在上下文里的呈现, 少占 token。
- 和宿主的关系: 登记只包一层宿主 `ctx.tools` 接口, 无大改动; 宿主把完整工具定义静态写进上下文, 增删工具就改动前缀、缓存失效。
- 不做什么: 不改宿主执行管道, 不接管权限与审批。

#### 事件订阅(ccascade)

- 要做什么: 提供统一的事件订阅接口与管理。
  - 统一订阅: 订阅会话、回合、步骤、压缩等生命周期节点, 统一走一个订阅面。
  - 频率控制: 控制动作的调用频率; 多种周期的事件集中到同一步时, 按配置避免重复触发。
- 和宿主的关系: 宿主缺插件之间的订阅顺序契约。
- 不做什么: 不定义具体动作(由上层决定), 不做定时调度(定时唤醒归自主推进, 事件只是唤醒的来源之一)。
- 现状: 事件订阅散在 `rule-engine` / `flow-arbiter` / `task-engine` 各订阅点。

#### 命令注册(ccommand)

- 要做什么: 提供比宿主更复杂的命令管理。
  - 子命令结构: 多级子命令、参数解析与校验由本层统一管理, 不再各插件手写 dispatch。
  - 补全支撑: 把命令结构投影为结构化子命令表, 供 TUI 补全到子命令一级。
- 和宿主的关系: 宿主 `ctx.commands` 只提供 register / list / find / execute, 列表只含 name 与 description, 子命令散在 `input.hint` 自由文本, 复杂命令(多级子命令、参数解析、调用上下文判定)管不了。
- 不做什么: 不做模型侧工具注册, 不实现命令内容, 不改动宿主命令服务本身。
- 现状: 命令面散在 `flow-track` / `flow-arbiter` / `auto-approve` / `background-daemon` / `command-template`, dispatch 与子命令均为各插件手写。

#### 增员(cspawn)

- 要做什么: 派生新的执行者(子 agent / 同事会话), 并给出它们的身份与生命周期; 支持进程内委派与常驻独立进程两种形态。
- 和宿主的关系: 宿主 `ctx.subagents` 提供进程内、由父会话管理的委派(一次性或可续), 没有常驻成员与独立进程的形态; 常驻会话的身份认领与生命周期登记要自建。
- 不做什么: 不做任务分派与协作编排(不在本等级), 也不管成员之间怎么通信。
- 现状: `coagent`(常驻独立进程会话)、`command-template` 的 subagent 步骤(进程内一次性子代理)。

### 什么不是

- 共享: 建在「同步」之上(跨会话的 KV / 消息传递依赖时间与顺序), 不是最底层能力。
- 任务执行 / 编排: 是「多级记忆 + 约束 / 守卫」的组合派生, 不是原子能力。

## 基础能力(组合)

| 基础能力 | 包名&服务名 |
|---|---|
| [共享 / 通信](#共享-通信cchannel) | cchannel |
| [自主推进](#自主推进cpush) | cpush |
| [回忆](#回忆crecall) | crecall |
| [注入引导](#注入引导cguide) | cguide |
| [约束](#约束cconstrain) | cconstrain |
| [治理](#治理cgovern) | cgovern |

在底层能力基础上组合出基础能力, 组合可以嵌套(已组合出的能力可再被更高层组合引用)。

### 共享 / 通信(cchannel)

组合: `csync + cmemory`。

- 要做什么: 基于同步与记忆提供三个功能:
  - 消息传递: 一个会话向另一个会话发送消息, 消息作为同步共享状态经 csync 送达、等待与唤醒; 需要跨进程存续时经 cmemory 落盘。
  - 共享内容: 多个会话读写同一份 KV, KV 作为同步共享状态经 csync 保持一致并解决并发写冲突; 需要持久化的内容存于 cmemory。
  - 寻址: 提供稳定的目标标识, 供消息投递定位目标会话。
- 和宿主的关系: 宿主没有跨会话通道(只有只读的 `sessionQuery` / `sessionReference`), 同会话内的 peer mailbox 又出不了进程。
- 不做什么: 不做成员与归属管理(谁在组里、谁认领了什么), 那属于更高等级。
- 现状: `session-channel`。

### 自主推进(cpush)

组合: `csync + cmemory`。

- 要做什么: 按阶段自行推进, 不依赖用户输入: 经 cmemory 记住当前进度, 经 csync 取得定时; 解析推进规则, 在需要时唤醒自己或继续循环。
- 和宿主的关系: 宿主只有零散的单点能力: 目标状态(`goals`)、计划状态(`planMode`)、会话级提醒(`schedule`)、后台作业(`jobs`), 没有「任务树 + 阶段顺序强制 + 验收」的推进模型, 唤醒也只回到原会话。
- 不做什么: 不判断活干得对不对(验收标准由上层给), 不做多 agent 的分派。
- 现状: `task-engine`(推进与验收)、`flow-track` / `plan-mode`(阶段推进、顺序强制)、`background-daemon`(定时开始)。

### 回忆(crecall)

组合: `cmemory + ccascade`。

- 要做什么: 管理要召回的内容: 内容的保持由 cmemory 承担(跨压缩仍能召回), 本层管理要召回哪些内容, 经 ccascade 订阅节点、到节点时召回。
- 和宿主的关系: 宿主的压缩(`compaction`)就是把旧内容挤出上下文, 投影缓存只服务重建, 没有「跨压缩保持 + 按节点召回」。
- 不做什么: 不决定召回之后怎么用(注入交给下一层)。
- 现状: `rule-engine` / `pin-note` / `preference-analysis` 的召回层。

### 注入引导(cguide)

组合: `crecall`。

- 要做什么: 工作流控制的正向, 告诉模型该做什么: 命中条件成立时, 代替用户投递一条消息, 用注入的内容引导行为; 让「什么条件下注入什么」成为声明式配置。召回内容由 crecall 提供, 本层只做条件判定与投递, 节流 / 去重经 ccascade 的频率控制承担。
- 和宿主的关系: 宿主的系统提示贡献面在装配期固定, 会话事件要自己订阅再写, 也没有命中条件、节流与去重。
- 不做什么: 不做硬拦截(拦是守卫层面的事), 不提供命令。
- 现状: `rule-engine` / `pin-note` / `preference-analysis`。

### 约束(cconstrain)

组合: `cboundary`(取其中的约束面)。

- 要做什么: 工作流控制的负向, 拦截模型不要做什么: 在规划与目标层面设边界, 阶段该做什么、计划段的范围、验收算不算过, 越界就拦; 拦的判断依据来自推进状态(与 cpush 共享), 具体验收判定交给上层。
- 和宿主的关系: 宿主的计划模式只给只读段, 审批只管工具调用, 都不管计划范围与验收口径。
- 不做什么: 不判工具调用的准入(那是治理层面的事), 不改系统提示。
- 现状: 散在 `flow-arbiter` 的审查、`plan-mode` 的计划段范围与 `task-engine` 的验收边界。

### 治理(cgovern)

组合: `cboundary + ccascade + cmemory + ctool`。

- 要做什么: 为复杂控制规则提供实现机制, 其他插件只定义规则, 不必自建机制: 在动作发生前挂事件取上下文(如工具执行前记录具体命令), 供规则判定; 经 cboundary 挂门禁、ccascade 取事件、cmemory 留痕、ctool 取工具元数据。
- 和宿主的关系: 宿主的审批是逐次、fail-closed 的单点询问, 只在会话日志里留 `approval/asked` / `approval/decided` 两条, 没有策略化的自动应答, 也没有审计面。
- 不做什么: 不管规划层面的边界, 不改审批服务本身的语义。
- 现状: `auto-approve` / `security-guard`。
