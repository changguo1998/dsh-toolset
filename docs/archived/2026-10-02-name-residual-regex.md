## 问题（前审阅给出的最小反例）

`topLevelNameValues()` 的词法扫描**不识别正则字面量**，且「被跳过的片段不参与配平」→ 深度漂移 → 其后的嵌套 `name:` 被当成顶层，**仍可静默假阴性**：

```js
defineTool({ name: TOOL_NAME, pattern: /[)]/, meta: { name: "read" }, parameters: { path: { type: "string", required: true } } })
```

→ 现脚本报「已覆盖 1：read」、`exit 0`。同类：`name: mk({ id: 1 })` 里的 `(`/`)` 也会让深度偏。

## 决策（本条目只修 (e)；(b)(c)(d) 保留为过度保守项）

- **D1（正则字面量识别，启发式）**：遇 `/` 时按**前一个非空白字符**判定：若它是 `( , = : [ ! & | ? { } ;` 之一或位于切片开头 → 视为**正则字面量**，跳到配对的未转义 `/`（识别 `[...]` 字符类与 `\` 转义）；否则按除法运算符处理（不跳）。
- **D2（表达式取值配平）**：`name:` 的表达式分支（如 `mk({ id: 1 })`）在**收集后跳过整段**并按其括号计数（用 `matchBrace` 类逻辑或自算深度），避免内部括号影响后续深度。
- **D3（测试）**：① 审阅最小反例（正则含 `)` + 嵌套 `name:"read"` 在前、真名在后）→ 必须**不**报「已覆盖 read」，必须未解析且 `exit 1`；② `name: mk({ id: 1 })` 形态同理；③ 既有 120 例不回归（尤其 `name: /x/` 类字面量不要被误跳）。
- **D4（反向验证）**：撤 D1/D2 → ①② 必失败；还原逐字节。
- **D5（文档）**：README 的「已知残余漏报（未闭合）」段改为「已修（正则/表达式配平）」并注明启发式边界（如 `/` 作除数时的判定依赖前字符）。
- **D6（不做）**：(b)(c)(d) 三条过度保守项**保留**（另条目跟进或不修）；不做完整 JS 词法分析器。
