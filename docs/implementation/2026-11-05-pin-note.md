# 跨压缩上下文保持插件 pin-note（接取条目：docs/BACKLOG.md「跨压缩上下文保持插件 `pin-note`」）

状态：调研　　开启：2026-11-05　　关闭：
本文件是本任务唯一的追踪文档与文档改动位置；计划外的文件不改。

## 目标

模型能把任意内容登记为「跨压缩保持」，登记后每轮都出现在模型可见上下文；手动压缩后依然在场。工具面 `pin_note` / `note_list` / `note_remove`（命名 2026-11-05 已定稿）。

## 调研（来源：宿主源码 `~/GithubRepos/deepseek-harness` @ `8bd073392e`，2026-11-03；本仓 memory-base / rule-engine 文档）

### 1. 四条「跨压缩」通道（逐条核实）

| 通道 | 锚点 | 语义 | 对本插件的适配 |
| --- | --- | --- | --- |
| A `agent/pre-step` 折叠 | `packages/core/agent/src/runtime-types.ts:350`；提交点 `agent-loop/src/agent.ts:463-473` | 每 step 询问，返回 `{kind:'enter', messages}` 可插入消息；插入的消息按 `user/message` + `surfaceOp:append` 落进会话日志 | 能保证每 step 都在场（压缩后下一步立刻补回）；代价是每 step 落一条历史 |
| B `agent.inbox` | `agent.ts:594-603`（`additionalContexts` 进 next-step）；`agent-instructions` 的 `prepend` / `replace` / `remove` 用法 `packages/context/agent-instructions/src/index.ts:245-270` | 待消费消息在 step 边界被 claim，只注入一次 | 单次注入，不随压缩自动补回 |
| C `tools/post-execute` 的 `additionalContexts` | `agent.ts:594-603`；本仓 `escalation-hint` 同款 | 工具调用后附加，进下一步 inbox，天然不进日志 | 只能挂在工具调用后，不能每 step 自发 |
| D `systemPrompt` 组装面 | `packages/core/system-prompt/src/index.ts:15,452-575`（section / context / variable / tools / assemble）；使用点 `agent.ts:446-461` | 每请求组装并渲染，属 system prompt；surface node 0 的 `system/message` **永不进压缩区**（`packages/compaction/compaction-basic/src/region.ts:110-111`） | 语义上最贴近「一直在场」；改动会触发 `system/message` 提交，节点形态与成本需实现时实测 |

### 2. 官方先例（可直接照抄的写法）

- `agent-instructions` 在 `agent/pre-step` 里把指令消息**折叠进 `decision.messages`**，并按「payload 相同」判断是否已在 `surface.nodes` 或本轮已 claim 的消息里（`index.ts:245-258`、`:330-356`）；未进入时用 `inbox.prepend` / `inbox.replace` 只留一条（`:259-270`）。这解决了「每 step 重注入但不重复堆积」。
- 同一插件用 `tools/result` + `step/end` 决定何时刷新（`:311-374`），说明「内容变化后下一次边界补回」的时序可控。

### 3. 存储面（本仓）

- `memory-base` 的 `registerKind({kind, writableTiers, preWrite})` 返回 `MemoryScope`（`put` / `forget`），写隔离按层（`memory-base/README.md:17-18,29-47`）；P 层库惰性创建、带隐私闸与容量控制。
- `memory-base` **不注册模型侧写工具**（模型侧只有只读 `memory_query`，`README.md:82-88`）→ 本插件必须自己注册 `pin_note` / `note_list` / `note_remove`。
- 检索排序 U > P > S，本插件只按 kind 精确列举，不走检索。

### 4. 关键约束

- 从 `agent/pre-step` 折进 `decision.messages` 的内容**会落进会话日志**（`agent.ts:463-473`），每 step 一条 → 长回合会反复落同一段正文（压缩后会重新落）。要么接受这个成本，要么走通道 D。
- 通道 D 的内容属 system prompt，不进压缩区，但每次变动会提交 `system/message`；稳态（内容不变）不重复提交（`agent.ts:452-461` 的 `startsRequestSeries` / 变更判断）。
- 模型侧写、读、删工具都要过 `security-guard` 的登记（命令文本与文件路径类参数）；本插件参数是纯文本，不进登记表。

## 决策

- 决策项 1 = 注入通道（用户 2026-11-05 裁定）: **a** —— `agent/pre-step` 折叠进 `decision.messages` + `agent.inbox` 只留一条（照 `agent-instructions` 先例）。理由: 每步都能补回（压缩后立即在场），且靠 payload 相等去重不堆积; 通道 D 只管 system prompt，覆盖不到回合中段。
  - a. A + B 组合（照 `agent-instructions`：pre-step 折叠 + inbox 只留一条）
  - b. 只走 D（systemPrompt section，稳态不重复写日志）
  - c. A + D 组合（内容进 system prompt，pre-step 兜底压缩后的回合中段）
- 决策项 2 = 存储（用户 2026-11-05 裁定）: **a + S 层** —— 用 `memory-base`，`registerKind({kind:"pin", writableTiers:["session"]})`，条目落 S 层会话库。理由: 复用隐私闸 / 容量 / 分块，不重复实现持久化; 与决策项 4 = a（会话级）一致。依赖面: S 层写入需 `sessionId`（取 `agent.session.id`）且 `session-paths` 服务已挂载，否则 memory-base 按明示例外报错——本插件在服务缺席时告警并降级为不写入。
  - a. `memory-base`（复用隐私闸 / 容量）
  - b. 自建 `sessionProjections` 单元（与记忆库解耦，但要自己实现持久化与容量）
- 决策项 3 = 注入粒度与上限（用户 2026-11-05 裁定）: **不做条数与容量的硬限制** —— 以「建议总量 < 10K 字符」为软口径, 超量只提示不拒绝; 工具描述与注入引导写明「只保留大致思路、用户的风格要求这类要点, 不贴大段原文」。理由: 硬上限会挡住正常用法, 引导 + 软阈值足以控制 token 成本。
  - a. 每条 pin 一条消息（缺省, 上限只作提示）
  - b. 合并成一条「已登记保持项」清单消息（省 token，逐条可读性下降）
- 决策项 4 = 作用域（用户 2026-11-05 裁定）: **a** —— 会话级（S 层），随会话结束失效。
  - a. 会话级（S 层）——随会话结束失效
  - b. 项目级（P 层）——跨会话保留

### 2. 存储 `src/store.ts`（读面已核实, 见步骤 2）

- 写：`ctx.memory.registerKind({ kind: "pin", writableTiers: ["session"], preWrite })` → `MemoryScope.put({ content, tier:"session", sessionId, title?, importance: 4 })`。`sessionId` 取 `exec.agent.session.id`（同 `coagent/src/tools.ts:31-34` 的 `callerSessionOf` 取法）。
- **读（关键）**：全局 `list` 会跳过 S 层——`memory-base/src/index.ts:388` 明确 `if (isSessionTier(tier)) continue;`，且 `tiers.list` 只遍历**已打开**的库（`tiers.ts:248-269`），所以 `list({tier:"session"})` 不可靠。改用 bundle 的层读面：
  - `const bundle = await ctx.memory.whenReady()`（`MemoryBundle.tiers`，`memory-base/src/index.ts:214-222`）；
  - `const store = await bundle.tiers.openExisting("session", sessionId)`（`tiers.ts:185-196`，只开不建）；
  - `store?.kb.listRows({ kind: "pin", limit: 50 })`（`knowledge.ts:520`，`ListOptions.kind` 必填）。
- 删：`store?.kb.evict(ids)`（与 `tiers.ts:286-289` 同款），**不用** `scope.forget`——它只作用于已打开库且 S 层依赖 `lastSessionId`（`scope.ts:116-133`）。
- 读取时机：每步 `pre-step` 读一次（`listRows` 走同步 SQLite，量级 < 50 行）；若真机显示开销明显，再加「写入后失效、平时缓存」的会话内缓存（实现时可留 TODO 注释，不预先优化）。
- `preWrite`：内容为空或 < 20 字符 → `accept: false`（避免碎片登记）。
- 建议体量：`totalChars = Σ content.length`；≥ 10240 时返回 `hint`，不拒绝（决策项 3）。

### 3. 注入 `src/inject.ts` + `agent/pre-step`

- 监听 `agent/pre-step`：`const decision = await next()`；随后 `desired = buildMessage(records)`（一条 user-role 消息，正文形如 `[pin-note] 跨压缩保持项（N 条）：\n1. …`）。
- 去重与落位（照 `agent-instructions/src/index.ts:245-356`）：已在 `decision.messages` / `session.surface` 同 payload → 不插；否则插在 `decision.messages` 最后一条已 claim 消息之后；同时 `agent.inbox.nextStep` 的同类旧消息只留一条。
- 无记录 → `desired = undefined`，清 inbox 残留（解挂 / 全删后零注入）。
- 消息形状照 `escalation-hint/src/index.ts:98-106`（`{id, role:"user", content:[{type:"text", text}], source:{kind:"pin-note"}}`）——该先例已证明运行时接受自定义 source kind。

### 4. 工具面 `src/tools.ts`（`ctx.tools.register`）

| 工具 | 参数 | 行为 |

### 5. 测试清单

| 用例 | 断言 |
| --- | --- |
| 登记 → 下一个 step | `decision.messages` 里出现一条 pin 消息，正文含登记内容 |
| 连续两个 step | 第二条 step 里**不重复插入**（surface 已有同 payload） |

| `note_remove` 后 | 下一 step 无注入；inbox 残留被清 |

### 8. 风险与未决点

- **S 层读面**（已从「未决」降级为「按 §2 的 bundle 读面实现」）：`bundle.tiers.openExisting("session", sessionId)` 只开不建，本会话没写过时返回 `undefined` → 按「零条保持项」处理（不报错）。**残留风险**：`whenReady()` 返回的 `tiers` 属 memory-base 内部结构面（不是公开服务契约），宿主或本仓改结构时会断——实现时写一条注释锚到 `memory-base/src/index.ts:214-222`，并在 README 记「结构性依赖」。
- **每 step 落一条日志**：同 payload 不重复插（靠相等判断），压缩后必然再插一次（这正是目的）。
- **消息来源标记**：`escalation-hint` 已用自定义 `source.kind` 且工作正常（`escalation-hint/src/index.ts:104`），同一写法无需额外确认。
- **S 层写入依赖 `session-paths`**：服务缺席时 memory-base 按明示例外报错 → 本插件告警并降级为「不登记」。
