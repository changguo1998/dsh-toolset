# 内容变更规范（详版）

> 职责：本仓库所有内容变更（文档 / 代码 / 配置）的标准流程与落地细则
> 不负责：协作命令与构建方式（见 `AGENTS.md`）、宿主接口知识（见 `docs/host/`）
> 过期条件：流程调整时更新（简版同步在 `AGENTS.md`）

## 1. 适用范围

- 适用于**任何**改动：不论范围大小、不论种类（文档、代码、配置、目录结构）。
- 执行者可以是人，也可以是 agent；多 agent 可并行，每个**任务**由一份追踪文档承载。
- 「模块」= `TUI` 与 12 个插件包（herdr-integration / task-engine / knowledge-base / goal-contract / metric-loop / output-compress / fs-digest / hash-edit / ast-tools / security-guard / code-map / context-report）；跨模块的改动归**项目级**。

## 2. 分层与目录

| 文档 | 项目级 | 模块级 | 作用 |
| --- | --- | --- | --- |
| ROADMAP.md | `docs/ROADMAP.md`（待建，见 `docs/BACKLOG.md` #41） | 无（仅项目级） | 未来开发方向 |
| DESIGN.md | 无（架构分布在模块 DESIGN 与 `docs/host/`） | `<模块>/docs/DESIGN.md` | 架构设计 |
| BACKLOG.md | `docs/BACKLOG.md`（跨包条目） | `<模块>/docs/BACKLOG.md` | 可执行条目 |
| STATUS.md | `docs/STATUS.md` | `<模块>/docs/STATUS.md`（按需） | 对照文档：记录已实现内容 |
| implementation/ | `docs/implementation/` | `<模块>/docs/implementation/` | 进行中的追踪文档 |
| archived/ | `docs/archived/` | `<模块>/docs/archived/` | 已关闭的追踪文档 |

其他约定：

- 包入口 `README.md` 固定在包根（npm 惯例）；模块其余文档进 `<模块>/docs/`。
- `docs/host/` 是宿主面知识（官方接口研读、升级对照、包字典），**不参与本流程**，按自身「过期条件」在宿主变化时复核。
- 模块内部约定（如 TUI 的配色语义、提示分级、模块拆分约定）放 `<模块>/docs/design/`。
- 根 `archive/` 只归档**根级**已关闭文档；模块历史进模块自己的 `docs/archived/`。

## 3. 任务与条目

- **任务 = 一份追踪文档；条目 = BACKLOG 里的一行。二者不是一一对应**：一个任务可以同时接取多个条目，一次性完成。
- **接取**：把所接取的**每个**条目标记「进行中」（对每个条目而言这是第一次写，此后中途不再切换状态）。
- **完成**：把所接取的**每个**条目标记「完成」（对该条目的第二次也是最后一次写）；追踪文档只归档一次。
- **中途增减条目**：在追踪文档「规划」中更新说明；新增条目按「途中发现新问题」的规则登记，不悄悄并入。

## 4. 条目生命周期

1. **开工前**：对应层 `BACKLOG.md` 里要有可执行条目（编号接续），写清：内容、来源、落点、优先级。
1. **开工时**：所接取的每个条目标「进行中」；在 `<层>/docs/implementation/<YYYY-MM-DD>-<slug>.md` 建追踪文档，文件头列出本次接取的**全部条目**，并**先写「计划改动文件清单」**。
1. **过程中**：
   - 本任务的所有文档变更（调研、决策、过程记录、产物改动）都写进这一份追踪文档；
   - **计划外文件一律不改**——清单里没有的文件不碰，尤其不做「顺手改」「顺便优化」；
   - 途中发现的新问题：写进本追踪文档，并在 BACKLOG **追加新条目**，交由其他 agent 接取；
   - 若确需改计划外文件：先说明原因与影响，由用户临时决定改不改、谁来改，并把变更补进清单。
1. **完成时**：所接取的每个条目标「完成」；追踪文档从 `implementation/` 移入 `docs/archived/`；关闭前必须补齐「测试与证据」与「收尾」两节。
1. **关闭后回写**：按需更新 `DESIGN.md` / `README.md` / `ROADMAP.md` 各一次（内容型文档）。
1. **STATUS 例外**：`STATUS.md` 是对照文档（记录已实现的内容），其内容可由 BACKLOG 条目 + 追踪文档推导；**更新时机与执行者由用户临时决定**，流程不自动改它。

## 5. 提交询问点

在以下四个关键点**主动询问用户是否提交**（由用户决定提交与否、提交粒度；未获同意不提交）：

1. **决策完成后**（方案定稿、开始动手前）
1. **代码实现完成后**（实现完毕、尚未测试）
1. **测试通过后**（自检与真机验证通过）
1. **任务关闭后**（条目已标完成、追踪文档已归档）

## 6. 追踪文档模板

```md
# <任务名>（BACKLOG: <层>#<编号>[, <层>#<编号>...]）

状态：调研 / 决策 / 规划 / 实现 / 测试 / 关闭　　开启：YYYY-MM-DD　　关闭：YYYY-MM-DD
本文件是本任务唯一的过程记录与文档变更落点；计划外的文件不改。

## 目标
## 调研        （来源：官方源码 / 官方包 / 实测 / 既有文档）
## 决策        （选项 → 选定 → 理由）
## 规划        （任务拆分 + 计划改动文件清单 + 明确不做的部分）
## 实现记录    （按时间追加，含关键命令与结果）
## 测试与证据  （命令 + 输出 / 真机现象 / 残留检查）
## 收尾        （回写了哪些文档、遗留项、是否移入 archived/）
```

写作要求：状态字段任一时刻只取一个值；文件头的条目列表即为本任务的接取范围，超出即需用户裁定。

## 7. 命名与归档

- 追踪文档：`<YYYY-MM-DD>-<slug>.md`，slug 用英文短横线（避免中文文件名的编码差异）。
- 归档：模块 `docs/archived/` 放本模块已关闭追踪文档；项目级 `docs/archived/` 放跨包已关闭追踪文档；根 `archive/` 只放根级历史资料。
- 空目录不预建（git 不跟踪空目录），按需创建。

## 8. 提交

- 沿用 `AGENTS.md`：**未明确要求不 commit / push**；在 §5 的四个询问点主动询问，由用户决定。
- 一次提交对应一个逻辑改动，提交信息按 Conventional Commits（中文），可引用追踪文档路径。
- 提交前：`format` 改动文件 → 自查 diff → 确认追踪文档的「测试与证据」已补齐。

## 9. 常见情形

- **极小改动**（错别字、措辞）：同样走流程（条目 + 追踪文档 + 归档），保持记录完整。
- **一个任务接多个条目**：文件头列出全部条目，接取与完成时对每个条目各写一次状态。
- **跨模块改动**：条目放项目级 `docs/BACKLOG.md`，追踪文档放 `docs/implementation/`。
- **宿主升级**：条目放项目级；升级过程记录进追踪文档；宿主面知识文档（`docs/host/`）在关闭后回写。
