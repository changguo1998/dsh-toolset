## 待办

**#1 tmux 在 dsh 所在 window 内 detach 会让程序退出（切到别的 window 再 detach 才保活）**（来源：2026-10-12 用户真机报告）：**现象** —— tmux 里 dsh 跑在某个 window 时，**停在该 window** 按前缀 + `d`（detach）→ **dsh 进程退出、会话丢失**；先切到别的 window 再 detach → dsh 保活，重新 attach 回来画面正常。**绕法（暂）** —— 先切 window 再 detach。**待取证（开工第一步，别先改代码）** —— 到底是哪条机制把进程带走：① **SIGHUP 无处理器**：`renderer/terminal.ts:41-56` 的 `installExitHandlers` 只挂 `SIGINT`/`SIGTERM`（→ 恢复终端后以 130/143 退出），**没有 SIGHUP** → Node 默认动作直接终止，且**不走终端恢复路径**（画面可能残留在 raw / alt-screen 状态）；② **当前 pane 的 stdin 收尾被当成退出输入**：`renderer/index.ts` 只有 `stdio.resume()`（`:236`）与 `stdio.pause()`（`:398`），没有 `end`/`close` 语义定义，若 detach 时当前 window 的输入侧收尾被解读成「用户要走」就会落到退出确认 / 结束会话路径。**取证动作**：在原 window detach 时记录退出码、挂临时日志到 SIGHUP / `SIGWINCH` / stdin `end`·`close`、看终端是否残留 raw/alt 屏（残留 = 没走恢复路径 = 更像 ①）。**历史关联** —— 早前条目〈tmux 断连后 dsh 退出〉的产物是「退出确认防单字节误触」（`app/index.ts:330`）与「合成问答面板确认退出」（`app/index.ts:2882`）；本次是否为那条的漏网场景（进程级信号绕过确认）需一并判定。**期望** —— 站内直接 detach 也保活：进程不退出、不丢会话，重新 attach 后画面能正常重绘（SIGHUP / stdin 收尾都按「暂停写屏、恢复后重绘」处理；即便真要退出，也必须先恢复终端状态）。**落点**：`TUI/src/renderer/terminal.ts`（信号注册 SIGHUP + 恢复策略）、`TUI/src/renderer/index.ts` 与 `renderer/input.ts`（stdin `close`/`end` 语义）、`TUI/src/app/index.ts`（退出确认触发面 `:330` / `:2882`）、必要时 `TUI/src/main.ts:702`（退出兜底）。**验收**：tmux 内「停在本 window detach → 重新 attach」进程仍在、画面重绘正常、终端无 raw/alt 残影；「切 window 再 detach」行为不变；全量 `npm run test:tui` 绿 + 新增用例覆盖「SIGHUP / stdin 收尾不结束会话」。**估时**：1-3 h（取证 + 修；若只是补 SIGHUP 处理并暂停写屏约 1 h）。**优先级**：P2（直接丢会话，属数据面损失）。〔待办：2026-10-12 登记，取证结论待开工时补〕

**#2 运行中执行 colortheme 切主题会让 dsh 退出（profile patch 被写 → HMR 重启 tui 行 → dispose 走进程退出）**（来源：2026-10-12 用户真机报告）：**现象** —— dsh 跑着时执行 `colortheme dark|light`（`~/fff/config/aliases.d/35-colortheme.sh`）→ **会话中断、dsh 退出**。**已读源确认的机制链（四段）** —— ① `35-colortheme.sh:288` 的 `_fff_theme_dsh_profile_switch` 重写 `~/.dsh/profiles/fff/cordis.patch.yml` 里 `tui` 行的 `config.theme`（值变化时才写；无变化时 no-op 不写）；② 宿主 `@deepseek-ai/dsh-base` bundle 默认插入 `hmr`（`@deepseek-ai/dsh-hmr`）行，`config.root: []`，其注释即「Profile configuration reloads by default」，`dsh-hmr` 的 `Service.init` 对 `profile.patchPath`（=该 patch 文件）、`~/.dsh/cordis.patch.yml`、profile `package.json` 逐个 `watchConfig(... → runReload(refresh))`；③ 文件变更 → loader `entry.update` → cordis `Fiber.update(config)` → 无 `internal/update` 干预时 `this.restart()` = dispose + apply；④ TUI 的 disposer（`main.ts:152-155`）→ `app.dispose()`（`app/index.ts:1360`）→ `finishDispose()`（`:1385`）→ `renderer.close()`（`renderer/index.ts:392`）→ `exitOnClose ?? true`（`:172`）→ **`process.exit(process.exitCode ?? 0)`**（`:406`）。即「插件 reload 被当成退出路径」——`app/index.ts:1380` 注释明说插件 unload 属优雅退出覆盖面。**待取证（开工第一步，别先改代码）** —— 在隔离 profile（复制 fff profile 目录或新建）里启动 dsh，改其 patch 文件的 `theme` 值，记录进程退出码与 `loader` 的 `reload` 日志（cordis 侧 `showLog(entry, "reload")`；日志经 TUI stderr 桥进活动区）；顺便判定「任何 profile patch 写入（含 `scripts/install.sh`、手工改 patch）是否都会杀会话」。**期望** —— 运行中改 profile 配置不杀会话：无需重建即可生效的配置（主题）由 tui 自行热应用；确需重建的行才重启 fiber，且**fiber 重启不等于进程退出**。**候选修法（开工时裁定）** —— A：tui 接管自己的 `internal/update` waterfall（cordis 文档明说该钩子「can veto or replace the restart」），`theme` 等可热应用键就地生效、不 restart（顺带让 colortheme 免重启即时生效）；B：`exitOnClose` 改 false，只在真退出路径显式退出（风险：真退出时若事件循环不排空会挂住进程）；C：主题不再走 profile patch，改由 tui watch 一个运行期主题文件（`tui.config.json` 一带），需与 FFF 仓协同改脚本。**落点**：`TUI/src/main.ts`（apply / disposer / update 拦截）、`TUI/src/renderer/index.ts`（`exitOnClose` 语义）、`TUI/src/app/index.ts`（dispose 与 finishDispose 的退出职责）。**验收**：dsh 运行中执行 `colortheme dark|light` → 进程不退、会话保留、主题当次生效（或明确提示需重启）；`/theme` 与重启路径（`DSH_RESTART_EXIT_CODE` = 75）行为不变；全量 `npm run test:tui` 绿 + 新增用例覆盖「fiber 重启不退出进程」。**优先级**：P2。**关联** —— 若 #1 的结论也是「某条路径 dispose 了 App」，则两条的退出职责落在同一处（`finishDispose`），取证结论需合看。〔待办：2026-10-12 登记，取证结论待开工时补〕
