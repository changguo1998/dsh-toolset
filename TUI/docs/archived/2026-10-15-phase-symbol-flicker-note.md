# 相位符号闪烁引发版面抖动（排查沉淀，条目已删）

> 原 BACKLOG 条目「相位符号闪烁引发版面抖动（边框左右跳 + 会话区上下跳）」〔暂停〕于 2026-10-15 按用户裁定从 `TUI/docs/BACKLOG.md` 移除；本文件保留其排查沉淀，供后续在目标环境（远程 SSH → WezTerm → tmux）再现时参考（复现时按 P1 口径接取）。

## 现象与期望

- 现象：相位符号在实心 / 空心之间切换时不止符号本身变化 —— ① 边框（活动区与会话区的外缘框列 / 分隔竖线）左右跳动；② 会话区（历史 pane）整体上下跳动。用户补充三种表现：会话区用户块「空心时有空格、贴底；实心时无空格、多一空行；输入换行后空行消失只剩空格问题」；状态列 Agents 块「符号位置不变、都有空格，但折行位置变」；工具名字行「边框列随之左右跳」。
- 期望：相位切换只改符号字形，帧几何与行数逐项不变（同一列、同一行数、边框列不动、pane 顶边不动）。

## 疑似范围（两选）

- 症状与「相位两态的有效宽度不等」完全吻合：用户块符号格是写死 2 列（`src/app/layout/build-box.ts:510`）而格内容 = 符号 + 空格，符号若按 2 列计则格内容 3 列 → 溢出（空格被挤到下一行 + 多一近空行；输入换行时该行被 body 高度吸收 → 正是「换行后空行消失」）；Agents 块的 `hanging: displayWidth(sym)`（`components/StatusColumn.ts:453`）随相位变 → 折行点变；工具名字行由帧层整格改写（`layout.ts` 的 `markToolNameRows()`，管线按 1 列排版）。
- 宽度从哪来（两选）：(a) 终端对两态的光标推进宽度不同（绘制看起来一样宽也可能推进不同）；(b) 宽度实测跨块应答错配 —— 探测每块只等 N 个 `CSI 6n` 应答或 `max(30, 150/块数)` ms 超时、块间不排空，而应答不带请求标识（`renderer/index.ts:347-364`、`renderer/input.ts:179`）→ 迟到应答落到下一块的等待者，相邻符号宽度错位；且 `WIDTH_PROBE_ATTEMPTED` 使每个码点只测一次，错值整个会话生效（`layout/markdown.ts:475-495`）。

## 判据（真机一条命令，逐符号单测绕开批量探测）

`for g in ● ○ ■ ✓; do printf '\033[1;1H%s\033[6n' "$g"; head -c 20 /dev/tty | cat -v; echo; done`

- 单测宽度不等 ⇒ (a)；单测都 1 列而 app 内实测不等 ⇒ (b)。

## 修法候选

1. **等宽兜底（推荐）**：运行时若 `charWidth(●) !== charWidth(○)`，不切换字形（保持实心，只靠颜色）或从备用对里挑实测等宽者。
2. 三处布局改按 `charWidth(sym)` 预留（用户块符号格、工具名字行；Agents 的 hanging 已是实测值）——溢出 / 空行消失，但两态本身仍差 1 列，边缘仍会每秒动。
3. 探测加固（块间排空 + 列号单调校验 + 允许重测）。

落点：`layout.ts`（相位取源与 `markToolNameRows`）、`build-box.ts`（符号格宽度）、`components/StatusColumn.ts`（hanging 与闪烁档）、`renderer/index.ts` + `input.ts`（若走 3）。

## 复看与 dump 证据（2026-10-13）

- 重启后用户目视：用户块符号与工具名字行两处闪烁正常、排版无问题——本缺陷在重启后不复现。这与「宽度实测覆盖表只存内存、每次启动重测」（`layout/markdown.ts` 的 `setWidthOverrides` + 上文 (b) 分支）吻合 → 更支持「探测结果不稳定 / 错配」而非「终端对两态恒定推进不同」（若是后者，重启后应照样抖）。
- 环境线索（用户提出，重要）：复现时是远程 SSH → WezTerm → tmux；现在同一 tmux 用本机 kitty 看就正常 ⟹ 本缺陷与终端 / 字体 / tmux 客户端相关（tmux 自己应答 `CSI 6n`，宽度模型随环境变），不是纯代码路径问题，故不是「修一次就永久好」的类型。
- dump 证据（kitty 会话，115/116 符号）：`tmp/w.txt` —— `○ ■ ✓ ✗ △ ← →` 等 115 个全部 `measured=1`（与静态表一致），唯独 `●`(U+25CF) 未被成功实测（列表里有、dump 里没有 → 保留静态 1 列）⟹ 本会话两态宽度一致，不复现，与目视一致；同时排除「终端对两态恒定推进不同」在本环境的可能。
- 由此暴露的第二个缺陷（探测韧性）：漏测的码点会被 `WIDTH_PROBE_ATTEMPTED` 标记为「已发起」，整个会话不再重试（`layout/markdown.ts:475-495`）→ 漏测 = 静默退回静态值；若环境真按 2 列渲染，就永久错。

## 抓现场方法（下次复现时先做）

在复现用的那个环境（WezTerm+tmux）用 `TUI_WIDTH_DUMP=<项目 tmp 下路径> dsh --profile fff` 启动，复现后 `grep -E "25CF|25CB|25A0"` 取两态实测值（本仓 `tmp/` 是 bind-mount）；顺带记下复现前是否刚出现过新符号（探测批量下发，块边界最可疑）。
