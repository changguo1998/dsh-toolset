# 排查：正文里的表格与排版后展示的表格内容不一致（接取条目：`TUI/docs/BACKLOG.md`「#3 排查：正文里的表格…」）

状态：已关闭（修复已合并 `844ec9f`；SPEC §3.2 / §15.5 与 TUI BACKLOG 已由主分支回写）　　开启：2026-10-22　　关闭：2026-10-23
本文件是本任务唯一的过程记录与文档变更落点；计划外的文件不改。

## 目标

复现并定位「正文里的 markdown 表格」与「排版后展示的表格」内容不一致的根因：差异发生在解析（表格识别与切分）、宽度求解（水位法压缩 / 返回 null 退回文本行）、还是渲染（Box 组装 / 格内折行 / 底色）。

本阶段交付以**结论**为主：差异形态清单（丢字 / 串列 / 换行错位 / 整表退化）+ 最小复现 + 修法建议；确认为缺陷后再动手修。

边界：不改既有「宽度不足时不截断格内容」的裁定；不替换 markdown 解析实现（除非定位到解析层缺陷）；不改紧凑模式与思考行不建表的既有口径。

## 调研

来源：源码阅读 + 本机实测（2026-10-23，`node --experimental-transform-types` 直接调 `splitCells` / `parseTableAt` / `buildContentRows`，脚本不落盘）。表格样本按真实回复形态手工构造（未取会话原文文件；如后续需要，可用 `session.v4.jsonl` 复核）。

**对照口径**：① 原文行 → ② `parseTableAt` 的 `TableSpec`（切出的格文本与列序）→ ③ 出帧行文本（`buildContentRows`，内容区宽 40 至 60）。

**差异形态清单**（逐条带实测证据）：

1. **解析层 · 未转义管道切列（丢字 + 串列）**：`splitCells`（`table.ts:100-127`）只认反斜杠转义，不识别行内代码 / 链接里的 `|`。
   - `| `a|b` | 或 |` + 分隔行 → 数据行切成 `["`a", "b`"]`（表头 2 列）：第 2 列「或」**丢失**，``` b`` 串进第 2 列；出帧为  ```┃ `a   │ b` \`（裸反引号）。
   - `| [x](http://a/b?c=1|2) | 说明 |` → URL 在 `|` 处切断，`2)` 串列。
   - 口径说明：GFM 规范要求表格里的管道写成 `\|`（**包括行内代码内**，见 <https://github.github.com/gfm/#tables-extension->），未转义时 GitHub 也切列。故这是**作者侧输入问题**（TUI 与 GFM 同口径），但出帧的裸反引号 + 丢字观感会让用户认为表格内容坏了。
2. **解析层 · 行内代码内的转义管道保留反斜杠（增字）**：`splitCells` 把 `\|` 原样（含反斜杠）放进格子；`parseInlineMarkdown` 的 code span 分支按**原文**输出（不做反斜杠还原），于是 `` `a\|b` `` 出帧为 `a\|b`。
   - GFM 口径：切列阶段就应把 `\|` 还原成 `|`，GitHub 渲染为 `a|b`。→ **真实的保真缺陷**（单元格多一个字符）。
   - 对照：非代码的 `a\|b` 出帧正确（行内解析会处理转义），只有代码跨度内泄漏。
3. **解析层 · 多余单元格被丢弃 / 缺格补空**：`parseTableAt` 用 `header.map(...)` 截断（`table.ts:169-186`）。`| a | b |` + `| 1 | 2 | 3 |` → 第 3 格「3」丢弃；`| 1 |` → 第 2 格补空。与 GFM 同口径，属规范行为（用户视角是丢字，但是既有语义）。
4. **宽度求解层 · 未发现内容丢失**：水位法压缩后格内按字符折行（CJK / 单词中间断），行高取各格最大行数、`valign: center` 居中；实测长单元格折成两行后**拼接即原文**（例：「负责把内容树摊平成终端行并」+「补齐底色」），行间 `─` 分隔未吞字。
5. **渲染层 · 退 null 整表退化**：`tableBox` 返回 null 时退回普通文本行（管道符原样、按文本折行）。实测 5 列 × 24 列宽：内容逐字保留，仅观感与表格完全不同（已知降级路径，符合条目「如实退回文本行而非变形」的期望）。
6. **与正文同口径的渲染差异（非表格特有，需在验收口径里排除）**：链接只显示可见文本（URL 不显示）、图片显示 `[alt] url`、`**粗体**` / `` `code` `` 去掉标记、单元格首尾空白被 `trim`。这些是 markdown 渲染的既定行为（正文也如此），不是表格独有的丢失。

**最小复现**（内容区宽 40，assistant final 行）：

```
| 语法 | 含义 |
| --- | --- |
| `a\|b` | 或 |     → 出帧 "┃  a\|b │ 或   "（应显示 a|b）
| `a|b` | 或 |      → 切列成 ["`a","b`"]，出帧 "┃  `a   │ b`   "（「或」丢失）
```

## 调研结论

差异层定位：**解析层的单元格切分**（`splitCells`，以及它与行内解析的口径衔接），不是宽度求解、不是 Box 组装 / 折行 / 底色：

- 现象 A（未转义 `|` 切列）：解析层；GFM 同口径，属输入需转义；是否做非标准增强是产品裁定。
- 现象 B（代码内 `\|` 泄漏反斜杠）：解析层；**保真缺陷，应修**（GFM 口径下切列时应还原 `\|` → `|`）。
- 现象 C（多余格丢弃 / 缺格补空）：解析层；与 GFM 一致，建议保持。
- 现象 D（压缩折行 / 退 null 文本行 / 链接只显示文本）：**不是缺陷**（既有裁定或 markdown 渲染口径）；条目的「逐字一致」验收需要排除标记与首尾空白。

## 候选修法（未选定，等用户裁定）

**修法 1（推荐）：切列时还原 `\|`**
`splitCells` 遇到 `\|` 时向当前格追加 `|`（而不是 `\|`）。范围：`TUI/src/app/layout/table.ts` 一处 + `TUI/tests/table.test.ts` 用例。取舍：1 行改动，与 GFM 对齐，修掉现象 B；不改变现象 A 的 GFM 行为。边界需覆盖：`a\|b`（普通）、`` `a\|b` ``（代码内）、`a\\|b`（`\\` 是转义反斜杠，其后 `|` 仍切列 —— 还原规则只吃「反斜杠 + 竖线」这一对，不信 `\\`）。

**修法 2（需产品裁定，偏离 GFM）：代码跨度内不切列**
`splitCells` 跟踪反引号配对（单 / 双反引号、未闭合边界），代码跨度内的 `|` 不切。取舍：更贴合作者意图（`` `a|b` `` 直接可用），但与 GitHub 行为不一致；要处理未闭合反引号、` `…` `、`\\|` 等边界，测试面比修法 1 大得多。

**修法 3（不推荐）：宽不足时截断格内容**
与 2026-10-01「宽度不足不截断格内容」的既有裁定冲突，且会引入新的丢失形态。

**修法 4（另一插件的事）：列数不匹配时提示**
`md-table-check` 已对回复正文的表格列数做检查；表格识别失败 / 列数不匹配时给作者提示属它的领域，不在本任务。

## 复现之一·行高测量与折行口径不一致（2026-10-23 定位并修复）

**结论**：`measureLeafRows`（`TUI/src/app/layout/table.ts:296-307`）用
`ceil(显示宽 / 列宽)` 估算格内行数，而实际折行走 `wrapFrameSegments`
（`TUI/src/app/layout/markdown.ts:754`）——下一个字符放不进剩余列时**提前换行**
（中文 2 列宽, 剩 1 列即换行, 每行浪费 1 列）。实际行数因此可能大于测量值, 而
`rowBox`（`table.ts:358-368`）把这个偏小值写死成 `heightFixed`：折行多出的那一行
**溢出到行 box 之外**, 该行没有左缘 `┃`, 也没有列分隔 `│`, 其后横线整体错位一行。

**复现**（`| 说明 | 备注 |` + `| 一二三四五 | 值 |`, 可用宽 13 → 列宽 [3,3]）：

```
┃  说  │ 备
┃  明  │ 注
┃ ═════╪═════
┃  一  │
┃  二  │ 值
┃  三  │
┃  四  │
   五              ← 该行丢 ┃ 与 │
```

单元级对照：cell `一二三四五`, 列宽 3 → 实际折行 5 行, `measureLeafRows` 得 4。

**命中面**（真实出帧, 宽度 24 至 160 逐档扫）：中文 2 列 0/137、3 列 5/137、
4 列 14/137、5 列 22/137、6 列 30/137；纯 ASCII 0/137。列越多越易中, 集中在压缩
生效的窄宽档。触发条件 = **列宽为奇数**且格内中文需折行, 与行内代码 / 链接 / 管道符无关。

**修法（已实施）**：`measureLeafRows` 改为与渲染同源——按物理行调
`wrapFrameSegments(parseInlineMarkdown(line), 格宽).length` 取行数（`table.ts`）；
用例「行高测量与折行同源：奇数格宽 + 中文折行时每行都有左竖线与列分隔」钉住
（每行 `┃` 开头、`│` 恰 1 个、整表等宽 13、折行内容不丢）。

**临时复现脚本**：`tmp/table-sep-repro.ts`（`node --experimental-transform-types` 直跑；任务结束前删除）。

## 修复·分隔行格数与表头不一致（2026-10-23 已实施）

**定位**：真机抓到屏上形态（主分支会话 2026-10-23 22:30, 窗口约 150 列）：表头 **5 格**、
分隔行 **4 格**、数据行 5 格, 全按原文打印。同一时刻的落盘文本是 5/5/5——所以差异不在会话文件,
而在排版链里「表格 → markdown 行」的**再生成**一步：

- `TUI/src/app/layout/pipeline/rows.ts` 的 `tableLines`：解析出表格 box 后要重新拼回
  `| a | b |` 形式的行交给旧渲染器, 其中分隔行的格数取的是 `box.aligns.length`,
  **不是表头格数**。两者一旦不等, 分隔行就比表头少列。
- 旧渲染器 `isTableStart` 要求表头与分隔行**列数相等**, 于是整表判不成表格 →
  退回普通文本行（原内容打印, 竖线外露）。

**修法（两处）**：

1. `pipeline/rows.ts` `tableLines`：分隔行按**表头格数**生成, `aligns` 只决定
   `---` / `---:` / `:---:`（缺的列按左对齐）——根因侧的防复发。
2. `layout/table.ts`：`isTableStart` 改为「列数**只许少、不许多**」——分隔行每格仍须形如
   `:?-+:?`, 少列时判为表格；`parseTableAt` 的 `aligns` 按表头列数生成（缺列左对齐）。
   这样上游任何一处把分隔行写短都不会再让整表退化成原文。

**验证**：

- 用例（`TUI/tests/table.test.ts`）：① `isTableStart` 少列 → true、多列 → false；
  ② `parseTableAt` 4 列表头 + 2 列分隔行 → 4 列 + 全左对齐；
  ③ 集成：该输入经 `buildContentRows` **成表**（有 `═`、无残留 `|`、每行 3 个 `│`）；
  ④ `boxToLines` 往返：`aligns` 只有 2 项时, 分隔行仍为 4 格。
- 端到端（`tmp/verify-fix.ts`, 用真机那段回复把分隔行改成 2 列喂进去）：往返后各表格行
  格数 `5,5,5,…`, 出帧成表、无残留管道符。
- 全仓 TUI：`npm run check` 通过, `npm test` 1748/1748 通过, `npm run build` 通过。
