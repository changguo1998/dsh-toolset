# 用户块终态：换 id 的 spliced 重块 + 归属优先人工输入（接取条目：`TUI/docs/BACKLOG.md` 的〈实时路径的终态归属会让注入块抢走人工输入的符号〉的恢复侧）

## 现象与真机定位

用户重启后报告：恢复的历史用户块基本正常，但**一条指令恒显示 `?`**（「等待子代理时每次轮询后 sleep 30」）。

先按「回合边界补齐」修法（`b534298`）核查：该修法让恢复侧 325 条里的 250 条拿到终态，但这一条仍是 `?`。用真机日志（会话 `tui-29301a68`，14552 → 14663 条事件）逐层核对，查出**两处独立成因**：

| # | 成因 | 证据 |
| --- | --- | --- |
| 1 | 同一条输入被宿主**换了 id 再 splice 一次**（`spliced@14258` id `50ce5ee7…`，与 `spliced@14282` / `user/message@14286` id `357088aa…` 正文相同）→ 旧的「按 id 去重」拦不住 → 画面上多出一个**永远等不到 `turn/end` 的重块**（恒 `?`） | 归一化后含该正文的用户块 3 条：`[aborted]` / `[-]` / `[success]`（第三条是用户后来引用它的那句话） |
| 2 | 恢复侧的终态回填按「该回合**最后一个**用户消息」落符号 → 该回合里排在人工输入之后的注入块（rule-engine / goal 回合 / 子代理结果）把符号抢走，人工输入留 `?` | 去重后该行 `turn=258 status=-`，而同回合的「Agent 9211ebb6…」注入块才是最后一条用户块 |

> 说明：条目原文把真机实例记成「turn 257 的 aborted 被抢」，实测不是——turn 257 的 `aborted / reason: user` 是这条指令**打断**上一个回合留下的记录；该指令本身属于 turn 258。上面的两处成因才是画面 `?` 的直接原因。

## 修法（`adapter/dsh.ts`）

1. `normalizeHistoryMessages` 首遍额外收集 `userTexts`（各 `user/message` 的正文），spliced 的 **user** 项正文命中即丢（按 id 去重保留）；真的重复发送同一句话不受影响——那两次各自都有 `user/message` 正文行，被丢的只是 spliced 副本。
1. 记 `humanUsers`（`source.kind === "user"` 的用户行下标）：终态回填**优先给人工输入**（取该回合最后一条人工输入），找不到才退回「该回合最后一个用户块」。
