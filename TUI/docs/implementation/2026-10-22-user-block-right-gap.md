## 目标

让用户块的右缘稳定：同一窗格下，行尾竖线 `┃` 到历史区右缘的距离**恒定**（等于选定的设计留白），不随文本是否含空格、行宽是否小于可用宽而变化；行内文字右缘与竖线的间距也按选定口径统一。

交付：含空格 / 纯中文 / 纯英文 / 含行内 markdown 四类长文本的一致表现 + 断言；不改助手侧留白与竖线语义。

边界：不改用户块的行内 markdown 排版；不动 `subagent` / 工具块等其它块的右对齐；是否保留右缘留白、补白放左还是放右，待用户定基线后再定。

## 调研

来源：源码阅读 + 本机实测（`node --experimental-transform-types` 直接调 `buildContentRows` / `measure` / `allocate`，2026-10-23；测量脚本不落盘）。条目正文里「含空格文本按词折行」的猜测**不成立**：仓库里没有按词折行，`wrapFrameSegments`（fill）与 `wrapLine`（measure）都是**逐字符**折行（`markdown.ts:733-770`、`primitives.ts:85-110`，grep `lastIndexOf(" ")` 零命中）。真实成因是另一条链路。

**复现**（内容区宽 38、用户块带首行状态符号、`USER_MIN_LEFT_GUTTER = 6`）：

| 输入（显示宽 L） | 块右缘 | 空隙 | 说明 |
| --- | --- | --- | --- |
| `汉×5 + " abc"×6`（L=34） | 23 | 15 | 折成 2 行、每行仅 17 列 |
| `汉×5 + " abc"×5 + " ab"`（L=33） | 23 | 15 | 同上 |
| `汉×5 + " abc"×6 + "x"`（L=35） | 38 | 0 | 只差 1 列，块反而贴右 |
| 混排长句（L=97） | 31 | 7 | 折 4 行、每行 25 列 |
| 纯中文 63 字（L=126） | 38 | 0 | 贴右 |

同一窗格内只改 1 列输入宽就出现「23 / 38」跳变，且**只有带状态符号时**出现（无符号时块恒贴右，实测 W=38/60/80 全部 0 空隙）——说明缺陷与文本宽度、与符号格都相关，不是「按词折行」。

**定位（本节结论的直接证据全部来自 measure / allocate 实测）**：

用户块结构（`build-box.ts:790-835`）：

```
h([ spacer(fill, min = gutter-1-symW = 3),
    content = h([ 符号格(fixed 2), 正文 styled(balance: true, suffix "┃") ]) ])
```

正文 `styled` 走 `fillStyled` 的平衡折行（`fill.ts:437-476`）：`C = ceil(L / R)`，`R` = 在 `maxW` 下的行数——**`C` 对可用宽高度敏感**。以 L=97 为例：可用宽 34 → R=3 → C=33；可用宽 32 → R=4 → C=25（一次掉 8 列）。L=34 的例子更极端：可用宽 34 → 1 行；可用宽 32 → 2 行 → C=17（掉 17 列）。

三层叠加导致缝隙：

1. **内层 h 少 2 列**：外层 h 给 content 的上界是 `38 - 3 = 35`；内层 h 里符号格固定占 2 列，正文实测拿到 35 后按 34 算 C。
2. **测出的宽是「收缩前」的**：`measureNode` 的 h 宽度用 `filledW += aw`（分配宽，`measure.ts:405-414`），随后才以分配宽重测子项；正文在缩窄 1 列后平衡宽从 34 掉到 17/25，但内层 h 仍报 35 → 外层只能给 spacer 3 列（其 min），而不是把剩余宽度全给它。
3. **缝隙留在内层 h 里**：内层 h 没有 fill 子项，`allocateWidths` 不会拉伸正文（`measure.ts:164-290`），所以 content 矩形 35 列里只画了 `2 + 18` 列，右侧 15 列空白 ⇒ 块停在 23，`┃` 贴不到右缘。

以 L=34 为例的完整数字（实测）：正文在 maxW=35 下量得 35（C=34+后缀）；内层 h = 2+35 = 37 > 35 → 正文被压到 33 → 以 33 重测：可用 32、折 2 行、C=17 → 正文实际 18；内层 h 仍报 35；外层 spacer 只拿 min 3；正文矩形 18、行宽 17 + `┃` ⇒ 块 23、空隙 15。

**与条目原猜测的差异**：条目写「外层 `h` 是 auto 宽、measure 只量到内容 + spacer 的 min」——后半句对，但「内容变窄」不是按词折行造成的，而是**平衡折行在小 1 至 2 列时 C 跳变** + **h 宽度用收缩前的分配宽**。另外，外层 h 的实际矩形是 pane 全宽（v 给子项全宽，`measure.ts:459-525`），所以只要 content 报的宽是真实的，spacer 就会吸收剩余、块自然贴右。

## 调研结论

差异层定位：**measure（宽测量）× fill（平衡折行）两侧口径不一致**，不是 fill 的补白侧问题、也不是外层 h 的 auto 宽问题：

- 触发条件：用户块**带首行状态符号**（内层 h 的固定 2 列子项）且正文平衡宽在 `可用宽` 与 `可用宽-1` 之间发生跳变；
- 直接病灶：`measure.ts` 的 h 宽度取「分配宽之和」（`filledW += aw`），与「按分配宽重测后的子项宽」不一致；配合 `balance` 的重算，把收缩前的宽冻结下来；
- 空出的是块内右侧：内层 h 无 fill 子项，多余列不会回流给 spacer；
- 无符号时单层 h，正文报的宽就是真实宽，spacer 吸收剩余 → 恒贴右（这解释了为什么问题只在部分消息上出现）。

## 候选方案（未选定，等用户裁定）

**方案 A：修 measure 的 h 宽度口径（根因修法）**
`measureNode` 的 h 在第二遍重测后，auto 子项的宽度改用重测值（fixed / fill / ratio 仍用分配宽）：`filledW += auto ? m.w : aw`。
取舍：一处改动（约 1 行 + 注释），修掉所有「h + 收缩型 auto 子项」的同类问题；**放大到全仓 h 的测量语义**，真机视觉需人工确认。已在临时副本（`tmp/proto-tui`，未进工作区）上验证：上述 L=33/34/35/97/126 五个用例全部贴右（空隙 0）；TUI 全量测试 1689 例里 1688 通过，唯一失败是 `/init：状态栏缩写 cwd…`——它按 `import.meta.url` 找仓库根的 `AGENTS.md`，副本目录没有该文件，属复制导致的环境性失败（原树该用例通过）。

**方案 B：用户块改成单层节点（局部结构修法）**
给 `StyledText` 增加「仅首行前缀」字段，符号格不再作为内层 h 的固定宽度子项，正文节点直接带 `balance + suffix + 首行前缀`。
取舍：不动通用 measure 语义，影响面只在用户块 + 新字段的 fill / measure 支持；代码量与测试量大于 A（新契约字段、首行宽度扣减、续行缩进口径），但风险更可控。

**方案 C：去掉用户块的平衡折行**
删除 `balance: true`（或只在无符号时启用）。正文自然宽 = 满可用宽，不再发生 C 跳变。
取舍：改动最小，但**丢掉既有的「两行等宽、避免末行只剩几个字」体验**（`user-width-balance` 的用例会变），属产品回退。

**方案 D：接受块不贴右，只把「右侧空隙」改成固定的设计留白**
在正文右侧显式补固定列（例如 `tail` 或 suffix 前补白），让空隙恒定但**不贴右**。
取舍：只是把不稳定的空隙变成稳定留白，不解决「窄块 + 大片空白」；与条目期望「竖线贴右缘」不符，仅作兜底。

**方案 E：调平衡宽度公式，减少 C 跳变**
例如仅在「不增加行数」的前提下收窄，或对 C 做上限约束。
取舍：直接缓解「文字突然变窄」的观感，但会改变既有平衡折行的行为与断言，需单独评审；可与 A 叠加。

## 需要用户裁定

1. **修法层**：A（measure 根因修法，原型已验证，但放大到全仓 h）/ B（用户块结构改造，局部可控）/ C（去掉平衡折行）/ E（先修平衡宽公式）——选哪个或组合。
2. **右缘语义**：块右缘应贴到内容区右缘（空隙 0，推荐；帧里另见的 2 列属 pane 外层边距，不属本块），还是保留固定的 N 列设计留白（若是，N 取几列、补在哪一层）。
3. **平衡折行是否保留**：保留则「块贴右、但文字行可能窄于可用宽（左侧留白变大）」是预期形态；不保留则文字撑满、行数可能增加。
