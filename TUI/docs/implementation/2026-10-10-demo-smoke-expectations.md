# 演示自检 3 项失败（接取条目：`TUI/docs/BACKLOG.md`「演示冒烟（`npm run demo -- --smoke`）3 项期望漂移」）

本文件是本任务唯一的过程记录与文档变更落点；计划外的文件不改。

## 目标

让演示程序的自检（`npm run demo -- --smoke`）全绿。原登记假设是「期望值过时、改期望即可」，本任务先核实这一假设，再决定改期望还是改代码。

## 调研

**结论：3 项失败都是真实缺陷，不是过时的期望。**

- 失败项（`npm run demo -- --smoke` 实测）：`step-header`、`activity-mixed-ordered`、`activity-mixed-activity-side`。
- 演示程序画画面走的不是真实运行时的路：它没有注入节缓存的接收口（`App` 的 `pipelineSink` 未传），所以每帧都是把**状态缓冲里的行重新放一遍**（`layout/pipeline/frame.ts` 的 `sectionsOf` → `replay.ts` 的 `sectionsFromBuffer`）交给六步流水线排版。**缺陷都出在这条「回放」路上**，真实运行时（宿主事件 → 块交付）不走它。
- 三类缺陷（探针实测，见「测试与证据」）：
  1. **步骤分隔线坏了**：回放路径产出的 step 头**没有时间戳**，还会多画——探针里看到 `╌╌ #0 ╌╌`、两条重复的 `╌╌ #1 ╌╌`（同一 step 两个头）。`step-header` 断言要求 `hh:mm:ss #1` 与 `hh:mm:ss #2` 同时出现，因此必失败；即使头画对了，它也可能被挤到活动区可视窗口之外（实测某一帧活动区只显示从工具行往下的内容）。
  1. **工具调用前后的正文被粘成一行**：同一步内先到 `助手文字甲`、再来工具调用与结果、再来 `助手文字乙` 时，接收层按「来源」把两段文字并成一条（`sections.ts` 的 `appendText` 不看块身份），渲染成 `助手文字甲助手文字乙` 一行，并整条归入会话区。演示里的 `混合中间输出` + `混合最终总结` 正是这样粘成一行、跑到会话区，于是 `activity-mixed-ordered`（要求按行号递增的先后顺序）与 `activity-mixed-activity-side`（要求中间输出留在回合区）双双失败。**目前没有任何待办条目覆盖这一类。**
  1. **提示行顺序错乱**：重试提示与压缩提示本该在工具调用之前，实测跑到工具行之后（同一根因家族：节顺序 ≠ 到达顺序，与 2026-10-10 新登记的「同 step 内 notice 与正文的到达顺序丢失」同源）。

**2026-10-10 追加（`policy-notice` 诊断：**非产品缺陷**）**：条目 4（会话区贴底）落地后 `policy-notice` 转失败，一度按 2×2 A/B（换回条目 4 前的 `layout.ts` 即通过，2/2 复现）判定为「贴底把提示折行续行挤出可见区」，并据此新登记了 BACKLOG 条目 19。随后把**编译产物** `dist/demo/main.js` 临时注入诊断（打印含提示文本的帧行，`dist/` 是 gitignore 的生成物，诊断后由 `npm run build` 覆盖复原）拿到实据：

```
DIAG frame=231 row=14 "                   │┃t）会分片输出这段话，模拟   │审批策略：never（工具调用自"
DIAG frame=231 row=15 "                   │┃真实流式。                  │动放行）"
```

两半**都在帧里**（活动区第 14、15 行），屏幕上看得到完整提示。失败来自自检的归一化：`flatFrames()` 把全部帧 `join("\n")` 后只剥 `[│\s]+`，而提示第二行前面隔着**会话区**那一行的回合分隔线（`╌╌ 22:10:16 ⇆2 ╌╌…`）——该字形不被剥掉，于是「第一半 + 分隔线 + 第二半」拼不成连续串。条目 4 之前失败不出现，只是因为会话区内容贴顶、提示第二行左侧那格恰好是空白（会被剥掉）；贴底后左侧换成有内容的行，断言就断了。

**结论与处置**：条目 19 **撤回**（不是产品缺陷，屏幕无丢失）；真正的缺口是**自检断言过弱**，归入本条目的收口（按 pane 分列断言，或归一化时补剥分隔字形）。条目 4/5 的落地代码无需改动。

## 决策

- **D1 不采用「只改期望」**：缺陷 1/2/3 都是可见画面错误，按条目验收口径「若判定为真回归 → 修码并补单测，不得只改期望」处理。
- **D2 范围并入后续条目**（用户 2026-10-10 裁定，选项 A）：
  - 缺陷 1（step 头无时间戳 / 多画 / 重复）并入条目「新回合后回合区出现多行『孤儿』步骤分隔线」一并修（同一落点 `panes.ts` 的 `headUpTo` / `declaredSteps` 口径）；
  - 缺陷 3（顺序错乱）并入条目「恢复的会话记录也保留用户块终态符号」「恢复的记录要能区分输入 / 正文 / 工具调用」这条回放保真线，以及新登记的「同 step 内 notice 与正文的到达顺序丢失」；
  - 缺陷 2 另立新条目「同一步内工具调用前后的正文被粘成一行」（接收层按来源合并、忽略块身份），本条目等它们关闭后复跑自检收口。
- **D3 本条目保持「进行中·阻塞」**，不做局部改期望：自检是对外可见的验收信号，先改期望会把真缺陷埋掉。
- **D4 不做**：不在本任务里给演示程序补接收口（那是「让演示走真实路径」的独立改造，属另一条线；本任务只负责自检能不能反映真实画面）。

**2026-10-10 追加（条目「step 分隔线补回合号」落地）**：step 头形制由 `hh:mm:ss #M` 改为 `hh:mm:ss ⇆N #M`，演示自检里 `step-header` 的正则 `\/\d{2}:\d{2}:\d{2} #1 \/` 因此必然失配（新文本里 `hh:mm:ss` 与 `#N` 之间多了 `⇆N` 段）。收口时该断言要按新形制改成 `hh:mm:ss ⇆N #M`，并同时处理第 8 行「缺陷 1」的另外两项（丢时间戳 / 多画与重复头）。
